## 1. Executive Summary

M2.2 expands the OpenAudit detection lab from 25 to 55 scenarios across eight security domains, adds new collectors and rules, and extends the evaluation infrastructure to support the expanded suite.

M2.1 established 100% precision and recall across 25 scenarios. M2.2 must preserve that baseline while extending coverage into domains not yet tested: privilege escalation paths, kernel hardening parameters, PAM authentication configuration, SUID/SGID binary enumeration, service account isolation, and SSH MaxAuthTries / Protocol constraints.

This document defines every proposed scenario, identifies required implementation changes, establishes acceptance criteria, and specifies the implementation sequence. No code is written until this document is approved.

## 4. Scenario Specifications

### Category 1: SSH Configuration (8 scenarios: S00–S07)

These preserve all 6 existing SSH scenarios and add 2 new ones targeting fields already collected but not yet evaluated by rules.

---

**S00 — SSH hardened baseline (control)**
- **Kind:** control
- **Threat:** Regression guard; confirms no false positives on a correctly configured host.
- **Setup:** `PermitRootLogin no`, `PasswordAuthentication no`, `PubkeyAuthentication yes`, `X11Forwarding no`, `MaxAuthTries 4`.
- **Expected findings:** none
- **Collector state:** `permit_root_login=no`, `password_authentication=false`, `x11_forwarding=false`, `max_auth_tries=4`
- **Rule behavior:** All SSH rules evaluate to empty.
- **Regression:** Existing S00. No change.

---

**S01 — `PermitRootLogin yes` (misconfig)**
- **Kind:** misconfig
- **Threat:** Brute-force root credential attack via SSH.
- **Setup:** `sed -i 's/PermitRootLogin no/PermitRootLogin yes/'`
- **Expected:** `linux.ssh.permit-root-login` (High)
- **Regression:** Existing S01. No change.

---

**S02 — `PasswordAuthentication yes` explicit (misconfig)**
- **Kind:** misconfig
- **Threat:** Password-based brute-force and credential stuffing.
- **Setup:** `sed -i 's/PasswordAuthentication no/PasswordAuthentication yes/'`
- **Expected:** `linux.ssh.password-authentication` (Medium)
- **Regression:** Existing S02. No change.

---

**S03 — `PasswordAuthentication` absent (OpenSSH implicit default) (misconfig)**
- **Kind:** misconfig
- **Threat:** Implicit password auth enabled because config key is absent.
- **Setup:** `sed -i '/PasswordAuthentication/d'`
- **Expected:** `linux.ssh.password-authentication` (Medium)
- **Rule behavior:** `password_authentication == None` → treated as `true` (OpenSSH upstream default).
- **Regression:** Existing S03. No change.

---

**S04 — `PermitRootLogin yes` via `sshd_config.d` drop-in (misconfig)**
- **Kind:** misconfig
- **Threat:** Drop-in override enables root login despite hardened main config.
- **Setup:** `echo 'PermitRootLogin yes' > /etc/ssh/sshd_config.d/50-override.conf`
- **Expected:** `linux.ssh.permit-root-login` (High)
- **Regression:** Existing S04. No change.

---

**S05 — X11Forwarding enabled (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** X11 protocol forwarding allows graphical session hijacking and privilege escalation via DISPLAY abuse.
- **Setup:** `echo 'X11Forwarding yes' >> /etc/ssh/sshd_config`
- **Expected:** `linux.ssh.x11-forwarding` (Low)
- **Collector state:** `x11_forwarding = Some(true)` (field already collected)
- **Rule required:** `SshX11ForwardingRule` — fires when `x11_forwarding == Some(true)`.
- **New rule:** `linux.ssh.x11-forwarding`, Severity::Low

---

**S06 — `MaxAuthTries` too high (≥ 6) (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** Excessive auth attempts increase brute-force feasibility.
- **Setup:** `echo 'MaxAuthTries 10' >> /etc/ssh/sshd_config` (replaces default line)
- **Expected:** `linux.ssh.max-auth-tries` (Low)
- **Collector state:** `max_auth_tries = Some(10)` (field already collected)
- **Rule required:** `SshMaxAuthTriesRule` — fires when `max_auth_tries >= 6` or when absent (OpenSSH default is 6, which meets the threshold).
- **New rule:** `linux.ssh.max-auth-tries`, Severity::Low
- **OpenSSH default:** 6; therefore `None` → treat as 6 → fire.

---

**S07 — `MaxAuthTries 4` (control)**
- **Kind:** control
- **Threat:** Regression; confirms the rule does not fire on a properly restricted value.
- **Setup:** Baseline already has `MaxAuthTries 4`.
- **Expected findings:** none
- **Rule behavior:** `max_auth_tries == Some(4)` → 4 < 6 → no finding.

- **Kind:** control
- **Threat:** Regression guard for S10.
- **Setup:** Baseline (default `www-data` has `nologin`).
- **Expected findings:** none

**S12 — Sudoers NOPASSWD for a named user (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** Any user with `NOPASSWD` in `/etc/sudoers` or a drop-in can escalate without authentication.
- **Setup:** `echo 'alice ALL=(ALL) NOPASSWD:ALL' >> /etc/sudoers`
- **Expected:** `linux.users.sudoers-nopasswd` (High)
- **Collector change:** Parse `/etc/sudoers` and `/etc/sudoers.d/*` for `NOPASSWD` entries; populate `nopasswd_sudo_users: Vec<String>`.
- **New rule:** `linux.users.sudoers-nopasswd`, Severity::High
- **Note:** `root ALL=(ALL) ALL` without `NOPASSWD` must NOT produce a finding. `%sudo ALL=...` without `NOPASSWD` must NOT produce a finding.

---

**S13 — Sudoers NOPASSWD in drop-in file (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** Same as S12 but via `sudoers.d` drop-in.
- **Setup:** `echo 'bob ALL=(ALL) NOPASSWD:/bin/bash' > /etc/sudoers.d/90-bob && chmod 0440 /etc/sudoers.d/90-bob`
- **Expected:** `linux.users.sudoers-nopasswd` (High)
- **Collector:** Same as S12 — drop-ins must be scanned.
- **Note:** File mode is correct (0440). The finding is about the NOPASSWD grant, not file permissions.

**S14 — Hardened sudoers, no NOPASSWD (control)**

- **Implementation note:** `iptables -L -n` will show `Chain INPUT (policy DROP)` — the existing check `!output.contains("Chain INPUT (policy ACCEPT)")` → `is_filtering=true` → Active. Scenario validates existing logic.

**S29 — Firewall with insufficient rules (informational)** ← NEW (Info-level)

- **Expected:** `linux.firewall.minimal-ruleset` (Info)

- **Collector change:** Add `rule_count: u32` field to `FirewallInfo`. Parse nftables output line count or rule count heuristic.
- **New field:** `FirewallInfo::rule_count` — count of distinct `rule` lines in `nft list ruleset` output.
- **Rule logic:** Fire if `status == Active && rule_count <= 2` (loopback-only stub).
- **False-positive risk:** Some minimal configurations are legitimate. Severity::Info is deliberate.

**S35 — SSH port 22 open on wildcard (informational)** ← NEW

**S36 — UDP port 53 (DNS) on wildcard (informational)** ← NEW
- **Kind:** misconfig
- **Threat:** An unintended DNS resolver exposed on a wildcard UDP interface can be used for DNS amplification attacks.
- **Setup:** Python UDP socket listener on `0.0.0.0:53`.
- **Expected:** `linux.ports.dns-publicly-exposed` (Medium)
- **New collector:** UDP port collector — parse `/proc/net/udp` and `/proc/net/udp6`.
- **New rule:** `linux.ports.dns-publicly-exposed`, Severity::Medium
- **Rule logic:** Fire if UDP port 53 is bound to a wildcard address.
- **Collector change:** Add `ListeningUdpPort` struct and `UdpPort::collect()` parsing `/proc/net/udp` (state `07` = UDP_CLOSE is not listening; state field for UDP is always `07`; need listening sockets which appear in `/proc/net/udp` with remote `00000000:0000`).

- **Control:** DNS only on loopback → no finding.

### Category 6: Privilege Escalation (7 scenarios: S38–S44)

---

**S38 — SUID binary outside of approved set (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** An unexpected SUID-root binary provides a local privilege escalation path.
- **Setup:** `cp /bin/bash /tmp/setuid-bash && chmod 4755 /tmp/setuid-bash`
- **Expected:** `linux.fs.unexpected-suid-binary` (High)
- **New collector:** SUID/SGID scanner — scan known directories (`/bin`, `/sbin`, `/usr/bin`, `/usr/sbin`, `/usr/local/bin`, `/usr/local/sbin`, `/tmp`, `/var/tmp`) for files with setuid or setgid bit.
- **New rule:** `linux.fs.unexpected-suid-binary`, Severity::High
- **Rule logic:** Report any file with SUID bit set where path is NOT in the allowlist of expected SUID binaries (see §4.6.1 below).
- **Collector change:** Add `SuidBinaryInfo` struct with `path: String`, `mode: u32`, `is_suid: bool`, `is_sgid: bool`. Add `SuidBinaryCollector::collect()` traversing known directories using `read_dir` recursively (one level only — no infinite symlink recursion).

**Expected SUID allowlist (conservative baseline):**
```
/usr/bin/sudo
/usr/bin/su
/usr/bin/newgrp
/usr/bin/chsh
/usr/bin/chfn
/usr/bin/passwd
/usr/bin/gpasswd
/usr/bin/mount
/usr/bin/umount
/bin/ping
/bin/ping6
/usr/bin/pkexec
/usr/lib/openssh/ssh-keysign
/usr/lib/dbus-1.0/dbus-daemon-launch-helper
/usr/sbin/pam_extraauth
```

**S40 — World-writable directory in `PATH` (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** A world-writable directory in `root`'s PATH allows an attacker to place a malicious binary that gets executed as root (PATH hijacking).
- **Setup:** `mkdir /tmp/evil && chmod 0777 /tmp/evil && export PATH=/tmp/evil:$PATH` (at audit time the PATH variable is captured).
- **Expected:** `linux.users.writable-path-entry` (High)
- **Collector change:** Capture `PATH` environment variable for the audit process. Parse each path component and check mode via `file_mode()`.
- **New rule:** `linux.users.writable-path-entry`, Severity::High
- **Rule logic:** For each directory in PATH, if world-writable or world-writable by group, fire a finding.
- **Implementation note:** `std::env::var("PATH")` is used in the collector — no additional system calls needed. Mode check uses existing `FileSystem::file_mode()`.

**S42 — `sudo` group with unexpected member (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** An unexpected account added to the `sudo` group gains full root escalation capability.
- **Setup:** `usermod -aG sudo alice`
- **Expected:** `linux.users.unauthorized-sudo-group-member` (High)

- **New rule:** `linux.users.unauthorized-sudo-group-member`, Severity::High
- **Rule logic:** Report accounts in the `sudo` or `wheel` group that do not appear in an operator-defined allowlist. Since there is no built-in allowlist, the rule reports ALL members of the `sudo` group for operator review.
- **Implementation note:** This produces an informational enumeration rather than a yes/no verdict. Consider Severity::Medium to avoid alert fatigue. The operator must verify the list.
- **Revised severity:** Medium (High creates too much noise for routine deployments).

### Category 7: Kernel and System Hardening (6 scenarios: S45–S50)

---

**S45 — `kernel.dmesg_restrict = 0` (misconfig)** ← NEW
- **Kind:** misconfig
- **Threat:** Unrestricted dmesg output leaks kernel addresses and hardware information to unprivileged users, aiding KASLR bypass.
- **Setup:** `sysctl -w kernel.dmesg_restrict=0` (or write `0` to `/proc/sys/kernel/dmesg_restrict`).
- **Expected:** `linux.kernel.dmesg-unrestricted` (Medium)
- **New collector:** Sysctl collector — read selected `/proc/sys/` paths directly via `FileSystem::read_to_string()`.
- **New struct:** `SysctlInfo` with fields for each checked parameter (initially 3).
- **New rule:** `linux.kernel.dmesg-unrestricted`, Severity::Medium

## 9. Known Limitations and Risks

### 9.1 SUID allowlist maintenance

The SUID allowlist in `SuidBinaryRule` is Ubuntu 24.04-specific. Different distributions, kernel versions, or installed package sets will have different expected SUID binaries. A finding rate of 100% recall requires the allowlist to be accurate for the lab container. The allowlist is the most significant FP risk in M2.2.

**Mitigation:** Define the allowlist as a constant in the rule, document that it is Ubuntu 24.04-specific, and add a note to the finding description that operator review is required.

### 9.2 Sudoers NOPASSWD parsing complexity

`/etc/sudoers` syntax is complex (aliases, `Cmnd_Alias`, `User_Alias`, `%group` entries, `ALL=(ALL:ALL)`). The M2.2 parser will handle only the common cases:
- `username ALL=(ALL) NOPASSWD:ALL`
- `username ALL=(ALL) NOPASSWD:/path/to/binary`
- `%group ...` forms will be noted in evidence but not expanded to member usernames.

**Mitigation:** Scope the M2.2 implementation to common patterns. Document limitations. Add a catalog note for complex sudoers parsing as a future M2.3 item.

### 9.3 UDP port collection gaps

`/proc/net/udp` does not carry a process name natively. The `inode → process` correlation via `/proc/pid/fd` works for UDP as well as TCP, but UDP sockets may not have a persistent owning process (e.g., DNS queries from systemd-resolved use short-lived sockets). The DNS exposure scenario (S36) uses a persistent Python listener, which will have a stable inode.

**Mitigation:** Implement process correlation for UDP using the same inode-matching approach as TCP. Accept that some UDP inodes may have no process correlation.

### 9.4 Kernel sysctl requires `/proc` access

The sysctl collector reads `/proc/sys/*` as plain files. This works as root and as an unprivileged user (most `/proc/sys/kernel/` entries are world-readable). Exception: some entries under `/proc/sys/kernel/` (e.g., `dmesg_restrict`) are readable by all but require root to modify. The collector is read-only and should work unprivileged for all three checked parameters.

**Mitigation:** Test the sysctl collector in both S11-equivalent (unprivileged) and root scenarios. Mark rules as `Unprivileged` if the proc path is world-readable; `RootRequired` only if it is root-only.

### 9.5 `linux.users.unauthorized-sudo-group-member` FP risk

Reporting all sudo group members as a finding will create noise on systems with legitimate sudo users. This is intentional behavior (enumeration for operator review) but needs clear documentation in the finding description.

**Mitigation:** Severity::Medium. Description must say "Review required — not necessarily a vulnerability." Evidence must list member names. Consider prefixing the rule ID with `linux.users.sudo-group-enumeration` to signal it is enumerative rather than definitive.

### 9.6 PATH collector and test isolation

The `EnvInfo` collector reads `std::env::var("PATH")`, which reflects the audit binary's own PATH. In the Docker lab, the binary runs as root with `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`. S40 must set PATH to include the world-writable directory before invoking the binary. This requires the `run.sh` to export PATH explicitly.

**Mitigation:** `run.sh` S40 block: `export PATH=/tmp/evil:/usr/local/sbin:...:/bin`. The binary inherits it. No engine change needed beyond reading `std::env::var("PATH")`.

### 9.7 iptables and Docker networking

Docker uses iptables internally (on the host) for NAT and bridge networking. Inside a container, iptables commands may be limited depending on capabilities. The `--cap-add NET_ADMIN` flag is already used in `run-lab.sh`, which should permit iptables operations inside the container. However, `iptables -P INPUT DROP` inside a Docker container could be risky if network connectivity is needed. Scenario S28 must be validated carefully.

**Mitigation:** S28 sets up iptables rules inside the container for the audit binary to inspect. The audit binary does not start the network — it only reads iptables state. The `--cap-add NET_ADMIN` capability is already granted. If the scenario causes container connectivity issues, use a mock approach via unit test instead and note the limitation.
